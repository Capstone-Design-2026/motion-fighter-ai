# REDBOOL

앉은 자세의 카메라 동작으로 플레이하는 대전 게임입니다. 스토리 모드와 같은 결투장을 두 노트북에서 보는 LAN **PvP 대전**을 지원합니다.

현재 개발 단계는 **v34 게임 콘텐츠·관절 진단 기록 통합 시험**입니다. 기존 인식과 스토리를 유지하면서 게임이 로컬 카메라 인식 프로그램을 직접 시작하고, 게임 안의 작은 패널에서 내 모습과 보정 상태를 확인하도록 구성했습니다. 최종 인식률이나 모든 PC의 성능을 보장하는 출시판은 아닙니다.

v34는 팀의 Unity 변경 `85ea2de`까지 통합하고, 원본 영상 없이 인식 관절 좌표와 처리 순서를 압축 기록합니다. v33.1의 Windows 소켓 소유권 수정과 기존 인식·개인 보정은 유지합니다. 새 공격용 메시의 표시를 두 화면에서 맞추기 위해 화면 통신 규약은 **30**으로 올라갔으므로 PvP 양쪽 모두 v34를 사용하세요. 별도 게임이나 Unity Editor Play를 함께 실행해 같은 포트를 점유하지 않도록 합니다.

## 게임 실행

빌드된 패키지에서 **Mac은 `REDBOOL.app`, Windows는 `REDBOOL.exe` 하나를 실행**합니다. Unity Editor나 Python 설치, 별도 카메라 명령어는 필요 없습니다. Windows는 실행 파일 옆의 지원 폴더도 함께 유지해야 합니다.

1. 스토리·결투·수련에 들어가면 카메라가 켜지고 **내 동작** 패널이 나타납니다. 최초 카메라 권한 안내를 허용합니다.
2. 양손과 팔꿈치가 화면에 보이도록 앉아서 **보정 버튼 또는 `C`**를 누릅니다. 같은 사람은 장면마다 다시 보정하지 않습니다. 사람이 바뀌면 `C`로 재보정합니다.
3. **접기**는 미리보기 표시만 쉬게 합니다. 동작 인식은 계속됩니다. 연결 문제가 생기면 **다시 연결**을 누릅니다.
4. 메인 메뉴로 돌아가거나 게임을 종료하면 게임이 시작한 카메라도 종료됩니다.

동작은 왼손 펀치→잽, 오른손 펀치→스트레이트, 왼손 레이즈→하이킥, 오른손 레이즈→로우킥, 양손 블락, 좌우 상체 기울이기→이동, 충전 후 X자→파운장입니다. 블락은 실제 유지하는 동안 적용하고, 팔을 풀면 해제합니다.

**파운장 게이지는 일반 공격이 블락에 막히지 않고 적중할 때 찹니다.** 맞기·막기·빗나감·파운장 자체의 적중은 충전하지 않습니다. 5회 적중하면 준비되며, 게이지는 막대로 표시합니다. 이 규칙은 이번 게임 콘텐츠 통합에서도 유지합니다.

## 두 노트북으로 PvP

두 노트북을 같은 LAN에 연결하고 각각 게임을 실행합니다. 한 명이 **PvP 대전 → 방 만들기**, 다른 한 명이 **방 찾기** 또는 방장의 로컬 IPv4 입력 후 **대전 참가**를 선택합니다. 방 찾기는 주소를 채우며 자동으로 다른 사람에게 접속하지 않습니다.

각 노트북은 자기 카메라를 처리합니다. 양쪽 수련을 마치면 전투가 시작됩니다. 호스트가 전투 결과를 결정하고 상대 화면으로 상태를 보냅니다. 인터넷 서버는 필요 없으며, 게스트가 호스트에 닿을 수 있어야 합니다. Windows 방화벽 안내가 나타나면 사용하는 로컬 네트워크에서 게임 통신을 허용하세요.

| 통신 | 포트 |
|---|---|
| 1P 카메라 입력 | 호스트 UDP 5065 |
| 2P 카메라 입력 | 호스트 UDP 5066 |
| 두 화면 상태·방 찾기 | 호스트 UDP 5067 |
| 내 카메라 미리보기·보정 버튼 | 각 PC 내부의 임시 loopback HTTP 포트 |

미리보기 영상은 상대 PC로 전송하지 않습니다. 현재 화면 통신 규약은 **30**이며, v34는 게임/패키지 버전입니다. 이전 규약의 게임은 같은 방에 연결하지 않습니다.

## 개발 및 패키징

- Unity **6000.4.5f1**을 사용합니다. Mac 개발과 Windows x64 데모를 지원합니다. 현재 Mac 카메라 실행 파일은 Apple Silicon용입니다.
- Editor에서는 기존 수동 Python 개발 흐름을 유지합니다. 통합 카메라는 실행 파일을 동봉한 실제 플레이어에서 작동합니다.
- Unity 빌드는 `RedboolLocalDemoBuild.Run`, 카메라는 Python 브랜치의 `scripts/build_camera_backend.py`, 최종 조립은 [`Tools/Developer/assemble_game.py`](Tools/Developer/assemble_game.py)를 사용합니다.
- Windows 카메라는 Windows에서 빌드해야 합니다. [Windows 카메라 빌드 작업](https://github.com/Capstone-Design-2026/motion-fighter-ai/actions/workflows/camera-backend-windows.yml)의 산출물은 **카메라 백엔드**이며 전체 게임 패키지는 아닙니다.
- 자동 Unity 검사·빌드에는 `UNITY_MCP_DISABLE=1`을 지정합니다. 관련 개발 플러그인의 DLL 자동 갱신이 검사 중 재컴파일을 일으키는 것을 방지합니다. 배포 게임의 통신 기능을 끄는 설정은 아닙니다.

자세한 조립 명령, 저장 위치, 카메라 없는 실행 검사는 [`Tools/Developer/V34_PACKAGING.txt`](Tools/Developer/V34_PACKAGING.txt)에 있습니다. 완성된 앱을 다시 만드는 과정이며, 사용자가 게임을 클릭할 때 Unity 빌드가 실행되는 구조는 아닙니다.

## 기록과 확인 범위

통합 패키지는 **원본 영상 없이 처리한 관절 좌표를 압축 저장**합니다. Lite 주 인식과 Full 보조 인식의 추정 좌표·신뢰도, 처리 시각·순서, 보정과 공격 이벤트를 함께 남깁니다. 별도 작업 스레드에서 압축하며, 카메라 실행당 관절 기록은 최대 128MiB입니다. 제한·저장 실패·빠진 구간은 명시하고 게임 처리는 계속합니다. 프레임을 일부러 건너뛰어 기록하지는 않습니다.

테스트 후 메인 메뉴에서 **기록 마무리 중…**이 끝나면 **진단 기록 저장**을 누르세요. 최근 3개 카메라 실행과 게임 로그가 담긴 ZIP 폴더가 열립니다. 완전히 닫힌 압축 파일만 크기·해시를 확인해 통째로 포함하고, 아직 쓰는 파일이나 손상·누락 파일은 `export_report.json`에 이유를 남깁니다. `landmarks.index.json`의 완전성·누락 정보를 확인한 뒤 재생합니다. 원본 파일은 삭제하거나 변경하지 않습니다. PvP 진단에는 양쪽 PC의 ZIP이 필요합니다.

관절 좌표는 모델의 추정값입니다. 원본 영상과 사용자의 의도 라벨이 없으므로 모든 실제 동작의 정답을 확정할 수는 없지만, 인식기가 어떤 좌표를 받고 왜 공격을 내거나 거부했는지는 훨씬 정확히 재현할 수 있습니다.

미리보기는 320×240, 최대 8fps로 제한하고 인식은 기존 처리 속도로 이어갑니다. 저장 영상 비교에서는 미리보기 유무 모두 약 30fps를 유지했지만, 이 결과가 실제 Windows 카메라나 두 PC의 전체 게임 프레임을 보장하지는 않습니다.

기존 v32 동작을 유지하는 회귀 검사, 여러 사람의 수련 기록 재생, 실제 Unity 접촉·가드·필살기 검사와 동봉 모델 실행 검사를 사용합니다. 손목이 화면 밖으로 나간 기록은 임계값을 낮춰 해결하지 않고, 카메라 패널에서 구체적인 자세·구도 안내를 제공합니다. 일반화된 인식률은 별도의 실제 사용자 검증이 필요합니다.
