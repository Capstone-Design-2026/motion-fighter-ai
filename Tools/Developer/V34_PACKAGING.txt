The Unity player owns one local REDBOOLCamera child while in tutorial/combat/PvP.
Story scenes retain one calibration. Returning to the main menu stops the child;
changing between story/P1/P2 starts the appropriate role. Closing the game stops
only its own child. The child's parent watchdog also handles unexpected exits.
Development/editor workflows remain manual; --redbool-external-camera opts out
in a packaged player. Physical cameras are never used by the automated checks.

User flow
1. Open REDBOOL.app (Apple Silicon Mac) or REDBOOL.exe (Windows x64).
2. Enter story/duel, or PvP 대전 → 방 만들기 / 방 찾기 and 대전 참가.
3. The local camera panel appears. Use 보정 or C with both wrists/elbows visible.
4. Each new person presses C. The existing v26-derived recognizer and bounded
   tutorial personal measurements remain the gameplay recognition path.
5. 접기 hides preview work while recognition continues. 다시 연결 restarts only
   the owned camera process. 메인 메뉴 → 진단 기록 저장 exports a small ZIP.

Transport and preview
Gameplay continues on the protocol30 LAN UDP connection: P1:5065,
P2:5066, shared game snapshots/discovery:5067. The host remains authoritative.
No internet server or relay is introduced. The two laptops need local reachability.
Discovery only fills an address; it never silently pairs with another game.
Camera JPEG preview is local loopback only: authenticated per-process HTTP,
320x240, target15fps (8fps under game/decode/request load), one latest-frame slot. It is never sent to the other laptop.
Unity status requests run at5Hz, preview decoding is bounded to one request at a
time. The main recognition loop is not throttled to the preview frame rate.

Default recording
No RGB/video is written. Every processed Lite observation and available Full
auxiliary observation is journaled with original JSON float precision, confidence,
model/frame identity and ordered engine-clock operations. Serialization and gzip
level1 run on a bounded worker queue. Complete chunks are indexed atomically.
Queue overflow, IO errors and the128MiB per-run compressed budget are explicit
coverage gaps; they never silently appear as a complete recording.
The diagnostic state/event/performance logs remain available alongside poses.

Files live in Application.persistentDataPath/CameraDiagnostics. After returning
to the main menu, wait for the owned camera child to finish flushing. The export
button includes the newest3 runs, complete indexed hash-verified chunks and a
bounded Unity log. Active .part chunks are excluded. Never tail-truncate gzip.
landmarks.index.json records source coverage; export_report.json records any
export omission. No video/models/unrelated files are included or deleted.
Coordinates alone are not human-labelled intended action ground truth.

Build on native target OS
Python branch: codex/tutorial-personal-pvp-20261112, requirements-backend-build.txt.
scripts/build_camera_backend.py creates an entire onedir REDBOOLCamera folder.
Windows GitHub Actions builds the x64 backend natively and validates imports,
model fingerprints, actual MediaPipe inference, loopback controls/preview and
graceful shutdown without opening a webcam. A Mac backend cannot replace it.

Unity uses6000.4.5f1, Mono, enabled build scenes via RedboolLocalDemoBuild.Run.
Build Unity first, then assemble the native backend into StreamingAssets:

python3 Tools/Developer/assemble_game.py --target mac --player /path/REDBOOL.app --backend /path/REDBOOLCamera --output /path/new-mac-package
python3 Tools/Developer/assemble_game.py --target windows --player /path/REDBOOL.exe --backend /path/REDBOOLCamera --output /path/new-windows-package

The assembler verifies target/model fingerprints, copies supporting files,
adds the Mac camera permission description and ad-hoc signs the Mac app.
This is local trial signing, not a notarized distribution release. Windows is an
exe plus its support folders; users click one entry point but must keep the folder.
No Unity Editor or Python installation is needed on the end user's laptop.

Safe native integration check
Run the packaged development Mac player with both flags:
--redbool-camera-check --redbool-camera-synthetic
and REDBOOL_CAMERA_CHECK_OUTPUT pointing to a new evidence directory.
This explicitly uses synthetic local images, never opens a camera and never sends
gameplay attacks. It verifies menu→PvP→menu→story, local preview/calibration controls,
role changes and cleanup, including destruction during pending shutdown.
Normal transport/gameplay test harnesses should use an unbundled player or pass
--redbool-external-camera so they cannot accidentally acquire a physical camera.

Release evidence and limitations
The unchanged recognition engine is checked against saved multi-person records.
New journal tests compare ordered replay with the original engine outputs and
exercise queue overflow, disk failure, cap, corrupt chunks and shutdown.
Native Unity checks cover diagnostics, ports, preparation, held guard, special
moves, scene routing and the new view protocol. The package release report gives
actual test counts and measured recording overhead; do not assume every hardware
or camera is validated by a successful build.
Real simultaneous Mac/Windows camera play remains the final user check. Preserve
entire Windows support folders. Mac local ad-hoc signing is not notarization.
